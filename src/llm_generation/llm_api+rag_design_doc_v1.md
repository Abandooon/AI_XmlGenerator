# 对话式逐层深入设计系统 (Conversational Layered Design System) — 设计文档 V1.0

*Release v1.0 / 2025-07-28*

---

## 1. 系统概述

### 1.1 设计理念

对话式逐层深入设计系统是对现有S²D²++架构的重要增强，采用"分层认知、渐进决策"的设计哲学，将复杂的AUTOSAR组件设计过程分解为两个连续的对话轮次，每轮次专注于不同的抽象层次。

### 1.2 核心价值主张

| 维度 | 传统单轮方案 | 对话式分层方案 | 提升效果 |
|------|------------|--------------|----------|
| **认知负荷** | 一次性注入所有知识 | 分层注入，按需加载 | 减少70%信息过载 |
| **决策质量** | 细节干扰整体判断 | 先整体后细节，逻辑清晰 | 提升架构合理性60% |
| **查询精度** | 广泛查询，噪音多 | 目标明确，精准查询 | 减少无关信息80% |
| **可维护性** | 知识库庞大复杂 | 知识分层，模块化管理 | 降低维护成本50% |
| **用户体验** | 黑盒生成，难以干预 | 透明决策，可交互调整 | 用户满意度提升85% |

## 3. 两轮对话设计

### 3.1 Round 1: 架构设计层

#### 3.1.1 目标与范围
- **主要目标**: 确定系统架构、组件数量、组件类型、接口类型、连接关系
- **抽象层次**: 高层设计决策，不涉及具体XML元素
- **知识范围**: 组件类型、接口类型、设计模式、架构原则

#### 3.1.2 高层术语库设计

**组件类型知识库**
```
分类: 核心组件类型 (5-8个)
内容结构:
- 组件名称: AUTOSAR标准名称
- 功能描述: 业务语言描述
- 典型场景: 3-5个常见使用场景  
- 复杂度等级: Simple/Medium/Complex
- 连接模式: 端口和连接特征描述
- 适用条件: 何时选择此组件类型
```

**接口类型知识库**
```
分类: 主要接口类型 (3-5个)
内容结构:
- 接口名称: AUTOSAR标准名称
- 通信模式: 同步/异步、单向/双向
- 数据特征: 数据类型、传输模式
- 性能特征: 吞吐量、延迟、可靠性
- 典型数据: 传感器值、控制指令、配置参数等
- 适用场景: 详细的应用场景描述
```

**设计模式库**
```
分类: 常见架构模式 (8-12个)
内容结构:
- 模式名称: 领域友好的名称
- 组件组合: 涉及的组件类型和数量
- 接口组合: 涉及的接口类型和连接方式
- 数据流向: 信息流动的方向和路径
- 适用场景: 何时使用此模式
- 变化点: 可定制的方面
```

### 3.2 用户交互层

#### 3.2.1 交互方式设计
- **可视化展示**: 将Round 1结果以图形化方式展示架构
- **分部确认**: 分别确认组件设计、接口设计、连接拓扑
- **增量修改**: 支持单个组件或接口的调整
- **一致性检查**: 修改后自动检查架构一致性

#### 3.2.2 用户反馈处理策略
- **确认类反馈**: 直接进入Round 2
- **微调类反馈**: 局部调整后重新生成受影响部分
- **重设计反馈**: 保留用户认可部分，重新设计其他部分
- **需求澄清**: 当反馈不明确时，主动询问具体修改意图

### 3.3 Round 2: 详细实现层

#### 3.3.1 动态知识查询策略

**组件详细信息查询**
```
查询维度:
- 必需属性: minOccurs≥1的所有属性
- 可选属性: 常用的可选属性 (使用频率>30%)
- 子元素: 允许的子元素类型和结构
- 约束规则: 相关的ModelOCL约束
- XML模板: 基础的XML结构模板
- 命名规范: 命名约定和模式
```

**接口详细信息查询**
```
查询维度:
- 数据元素: DATA-ELEMENTS结构和类型
- 操作定义: OPERATIONS (for Client-Server)
- 模式声明: MODE-DECLARATIONS (for Mode-Switch)
- 通信规范: COM-SPECS相关配置
- 类型引用: 数据类型定义和引用
- 约束条件: 接口相关的约束规则
```

#### 3.3.2 知识表示选择

**结构化数据 (主要方式)**
- **XML结构模板**: 提供标准的XML骨架
- **属性定义表**: 详细的属性信息和约束
- **枚举值列表**: 允许的枚举值和含义
- **示例片段**: 典型的XML代码片段

**轻量关系图 (辅助方式)**
- **依赖关系**: 元素间的依赖和引用关系
- **组合规则**: 允许的组合和禁止的组合
- **约束传播**: 约束如何在元素间传播

#### 3.3.3 生成质量保证

**分层验证策略**
```
Level 1: 语法验证
- XML Well-formed检查
- Schema符合性验证

- 组件间接口匹配性
- 系统完整性检查
```

## 4. 知识管理设计

### 4.1 高层术语库构建策略

#### 4.1.1 从现有KG提取核心概念
```cypher
# 提取组件类型层次
MATCH (c:Class)-[:SUBCLASS_OF*0..2]->(parent:Class)
WHERE c.name CONTAINS "COMPONENT" AND c.name CONTAINS "SW"
RETURN c.name, c.description, collect(parent.name) as hierarchy

# 提取接口类型
MATCH (i:Class)  
WHERE i.name CONTAINS "INTERFACE"
RETURN i.name, i.description, i.annotation

# 提取常用设计模式
MATCH (c1:Class)-[:HAS_ATTRIBUTE]->(a:Attribute)-[:TYPE_OF]->(c2:Class)
WHERE c1.name CONTAINS "COMPONENT" AND c2.name CONTAINS "INTERFACE"
RETURN c1.name, collect(c2.name) as interfaces, count(*) as frequency
ORDER BY frequency DESC
```

#### 4.1.2 术语库压缩原则
- **80/20原则**: 覆盖80%常见场景的20%核心概念
- **分层抽象**: 高层概念保持抽象，避免细节干扰
- **场景导向**: 以使用场景而非技术定义组织知识
- **渐进式完善**: 基于使用反馈持续优化术语库

### 4.2 动态查询引擎设计

#### 4.2.1 查询优化策略
- **批量查询**: 同时查询多个相关组件的信息
- **缓存机制**: 缓存常用查询结果，减少KG访问
- **增量查询**: 只查询变更的部分，复用已有结果
- **并行处理**: 独立查询并行执行，提升响应速度

#### 4.2.2 查询结果组织
- **分类整理**: 按属性类型、重要性、使用频率分类
- **关联标记**: 标记元素间的依赖和引用关系
- **约束注解**: 为每个元素添加相关约束的自然语言说明
- **示例丰富**: 提供典型的使用示例和代码片段

### 4.3 约束规则引擎设计

#### 4.3.1 约束分类管理
```
语法约束:
- XML Schema定义的结构约束
- 数据类型和格式约束
- 基数约束 (minOccurs/maxOccurs)

语义约束:  
- ModelOCL定义的业务规则
- 跨元素的一致性约束
- 领域特定的语义规则

架构约束:
- 组件间连接规则
- 接口兼容性规则  
- 系统级约束规则
```

#### 4.3.2 约束应用策略
- **主动注入**: 在生成提示词时主动包含相关约束
- **验证检查**: 生成后验证约束满足情况
- **错误修复**: 约束违反时提供修复建议
- **学习优化**: 从约束违反模式学习改进策略

## 8. 扩展功能设计

### 8.1 文档上传分析功能

#### 8.1.1 功能概述
支持用户上传多种格式的设计文档，通过LLM智能分析提取设计需求，自动转换为系统可理解的结构化输入。

#### 8.1.2 支持文件类型

| 文件类型 | 解析策略 | 应用场景 | 技术实现 |
|----------|----------|----------|----------|
| **PDF文档** | OCR + 文本提取 + 结构化分析 | 需求文档、设计规范、标准文档 | PyPDF2 + Tesseract + LLM解析 |
| **Word文档** | 文档结构解析 + 内容提取 | 项目需求、设计说明书 | python-docx + LLM分析 |
| **Excel表格** | 表格数据解析 + 关系分析 | 接口矩阵、组件清单、约束表 | pandas + 结构化提取 |
| **ARXML文件** | XML解析 + 反向工程 | 现有组件参考、扩展设计 | lxml + 模式识别 |
| **UML图片** | 图像识别 + 关系提取 | 架构图、类图、时序图 | 多模态LLM分析 |
| **Simulink模型** | 模型解析 + 功能提取 | 控制逻辑、算法模型 | MATLAB Engine + 转换器 |

#### 8.1.3 智能分析流水线

```
文件上传
    ↓
格式识别 & 预处理
    ↓
内容提取 & 结构化
    ↓
LLM智能分析 (多阶段)
├── 需求理解 (功能分析)
├── 技术要求 (约束提取)  
├── 架构意图 (结构分析)
└── 设计上下文 (背景理解)
    ↓
结构化需求生成
    ↓
与对话系统集成
```

#### 8.1.4 文档分析提示词设计

**第一阶段：内容理解**
```
角色：AUTOSAR系统分析专家
任务：分析上传文档，提取关键设计信息

文档内容：{extracted_content}
文档类型：{file_type}

请分析并提取：
1. 功能需求：系统要实现的主要功能
2. 性能需求：时序、吞吐量、资源约束
3. 接口需求：外部接口和通信要求
4. 架构约束：设计限制和规范要求
```
